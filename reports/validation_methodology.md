be stated explicitly if questioned in the viva.

## 3. Held-Out Well Split Methodology

This is the non-negotiable methodological safeguard for the project: **we
validate against geographically held-out CGWB wells never used in Kriging
or downscaling, not merely against the Kriged training surface.**

**Method:** Spatially stratified split (`held_out_split.py`).
1. The study region bbox is divided into a 10×10 grid of cells.
2. From each cell, 17.5% of the *unique wells* located in that cell are
 randomly selected for the held-out set.
3. Sparse cells (too few wells for the fraction to round to ≥1) are given
 a probabilistic chance to still contribute one held-out well, so
 held-out coverage isn't biased toward only densely-sampled cells.
4. All quarterly readings belonging to a held-out well are held out
 together — the split operates on unique wells, not individual reading
 rows (see note below).
5. Zero-overlap between train and held-out well IDs is enforced by an
 automated assertion (`assert_no_overlap`) and a corresponding pytest
 suite (`tests/test_held_out_split.py`, 8 tests, all passing).

**Reproducibility:** Random seed = 42, stored in `config/data_config.yaml`.
The split is idempotent — rerunning with the same seed reproduces the same
train/held-out membership exactly.

**Important implementation note (documented for defensibility):** The CGWB
dataset provides quarterly readings per well across 2013–2022 (up to ~37
readings for a single well). An early version of this pipeline mistakenly
performed the stratified sampling at the *reading* level rather than the
*well* level. Because held-out/train membership is determined by well ID,
selecting even a single reading from a well pulled that well's entire
multi-year history into the held-out set — with ~37 readings per well, this
meant nearly every well in the dataset got touched, inflating the held-out
fraction to 98.4% instead of the intended ~17.5%. This was caught before
any Kriging or model training occurred, by inspecting the printed
train/held-out counts against the expected 15–20% target. The fix:
deduplicate to one row per well, perform the stratified split on that
unique-well set, then rejoin all readings for whichever wells landed in
each split. A regression test (`test_split_handles_repeated_readings_per_well`)
now guards against this specific failure mode recurring.

**Final observed split (Maharashtra bbox, seed=42):**
- Total readings: 92,227
- Train: 76,154 readings (82.6%)
- Held-out: 16,073 readings (17.4%)

**Files (immutable from this point forward):**
- `data/held_out_wells/held_out_ids.csv`
- `data/interim/train_well_ids.csv`

These files must never be regenerated with a different seed or split logic
later in the project — doing so would silently reintroduce the circular
ground truth problem this entire methodology exists to prevent.

**Implementation note (fetch bugs caught and fixed during Phase 1):**
Two bugs were found and corrected in `gee_fetch.py` / `align_grid.py`
during this phase, both caught by inspecting output before proceeding to
Phase 2:
1. **Nodata contamination**: Sentinel-1/2 composites cover a region wider
 than a single satellite swath, so large portions of each monthly
 composite have no observation for that month. These masked pixels were
 initially exported as `0` (a physically invalid value for VV
 backscatter or NDVI) instead of being preserved as missing. Fixed by
 explicitly unmasking to a sentinel nodata value (`-9999`) before
 export, declaring it in the GeoTIFF's metadata, and propagating it as
 `NaN` through `align_grid.py`'s reprojection step rather than letting
 it blend into neighboring real pixels.
2. **GRACE date-filtering mismatch**: GRACE mascon solutions are
 irregular ~30-day windows that don't align to calendar-month
 boundaries the way daily products (CHIRPS, GLDAS) do. A strict
 `filterDate(month_start, month_end)` query missed many real,
 available GRACE solutions whose timestamps fell just outside a given
 calendar month. Fixed by switching to a nearest-match query
 (`fetch_grace_nearest`) that searches a ±45-day window around each
 target month and selects whichever available solution is closest in
 time, which is the standard approach for irregular-cadence satellite
 products.

## 5. Grid Alignment

**Method:** `align_grid.py` reprojects every raw raster source onto a
common 64×64 grid spanning the study region bbox, using bilinear
resampling (appropriate for continuous fields like precipitation, soil
moisture, NDVI, backscatter).

**Training wells** are rasterized separately onto the same 64×64 grid via
point-binning (`rasterize_training_wells`) — multiple wells landing in the
same cell are averaged. **Held-out wells are never rasterized into this
grid stack**; they are reserved exclusively for point-extraction during
evaluation (Phase 2/3), consistent with the anti-circularity requirement
in Section 3.

**Visual spot-check (completed):** `reports/grid_alignment_spotcheck.png`
confirms all five sources (CHIRPS, GLDAS, GRACE, Sentinel-1, Sentinel-2)
share identical spatial extent and correct co-registration, with no
shifting, flipping, or cropping mismatches between layers. Observations:

- **CHIRPS / GLDAS**: full coverage, smooth spatially coherent patterns —
 as expected for daily/3-hourly products.
- **GRACE**: renders as a small number of large rectangular blocks. This
 is expected, not a defect — GRACE's native resolution is ~300km, so a
 handful of coarse blocks is what real GRACE data looks like when
 resampled onto a 64×64 grid over an ~900km-wide study region. This
 coarseness is precisely why Phase 2's Random Forest downscaling step
 exists, and must not be mistaken for sub-kilometer accuracy anywhere
 in the final report (see Risk Register).
- **Sentinel-1 / Sentinel-2**: individual monthly composites often have
 low spatial coverage (e.g. 2–52% in spot-checked months) because a
 single month's satellite passes rarely cover the full ~900km-wide study
 region in one swath. Real captured pixels show physically plausible
 values (Sentinel-1: -25 to -8 dB; Sentinel-2 NDVI: 0.42-0.58); areas
 with no observation that month are correctly masked as missing (NaN)
 rather than defaulting to a false 0 value (see the nodata-handling fix
 documented in Section 4). This partial-coverage characteristic should
 be handled downstream in Phase 2/3 (e.g. temporal interpolation across
 adjacent months, or treating these as sparse covariates) rather than
 assumed to be full-coverage inputs.

## 7. Static Covariate: SRTM Elevation & Slope

Pulled once via `srtm_fetch.py` (source: `USGS/SRTMGL1_003`), aligned onto
the common 64×64 grid via the same `align_grid.py` pipeline as the Phase 1
monthly sources. Unlike CHIRPS/GLDAS/GRACE/Sentinel, these two covariates
are static (no time dimension) and reused identically for every date in
the training table. Both `srtm_elevation` and `srtm_slope` remain in the
v2 feature set unchanged (Section 9).

## 8. Kriging Methodology (Training Wells Only)

**Method:** Ordinary Kriging (`kriging.py`, `pykrige`, spherical
variogram), applied exclusively to **training wells** — the anti-
circularity boundary from Section 3 is preserved throughout Phase 2: held-
out wells are never Kriged, never used as RF features, and touched only
once, at the very end, by the validation script.

**Campaign-month aggregation (methodology correction):** An initial
version Kriged each *exact* reading date independently. Because CGWB field
teams read different wells on different specific days within the same
quarterly campaign (e.g. four distinct dates within May 2019 alone), this
fragmented the data into many sparse single-day slices — often only 1–2
wells each, insufficient for Kriging (which requires ≥3 non-collinear
points) and producing unstable surfaces even when it technically
succeeded. **Fix:** wells are now aggregated by calendar month before
Kriging (`krige_all_available_dates_by_month`, minimum 5 wells/month),
averaging any well's multiple readings within the same month first. This
gives each Kriging call substantially more points and a far more stable,
representative surface.

**Kriged surfaces produced:** 154 of 185 unique training campaign-months
successfully Kriged; 31 skipped for having fewer than the minimum well
count even after monthly aggregation (documented, not silently dropped).
This is unchanged in the v2 pipeline — v2 changes only the RF stage's
feature set and evaluation protocol, not the underlying Kriging step.

## 9. Feature Engineering (Revised for v2)

The RF/HGBR model predicts the Kriged surface from features built per grid
cell per date (`feature_utils.py`). **The v2 feature set (16 features,
adopted) differs from the original v1 feature set (11 features) in two
ways: Sentinel-2 NDVI is dropped (Section 12.2), and `row_norm`/`col_norm`
are reintroduced alongside four new "age" channels.**

**v2 feature set (16 features, current/adopted):**

| Feature | Description |
|---|---|
| `chirps`, `gldas`, `grace` | Instantaneous monthly covariates, matched under a base 90-day window with a 400-day fallback window (Section 11) |
| `srtm_elevation`, `srtm_slope` | Static terrain covariates |
| `month_sin`, `month_cos` | Cyclical calendar-month encoding |
| `chirps_roll3`, `gldas_roll3` | Rolling 3-month average |
| `target_lag1` | Nearest **prior** calendar-month Kriged (training-well-derived) surface at the same cell, matched under a 120-day window with a 365-day fallback |
| `lag_age_days`, `chirps_age_days`, `gldas_age_days`, `grace_age_days` | New in v2 — how stale each matched covariate/lag actually is, letting the model down-weight or otherwise account for fallback-window matches rather than treating a 400-day-old CHIRPS match identically to a fresh one |
| `row_norm`, `col_norm` | Grid-normalized spatial coordinates — reintroduced in v2; see the note below and Section 10 |

**v1 feature set (11 features, superseded):** `chirps`, `gldas`,
`sentinel2_ndvi`, `grace`, `srtm_elevation`, `srtm_slope`, `month_sin`,
`month_cos`, `chirps_roll3`, `gldas_roll3`, `target_lag1`.

**Note on `row_norm`/`col_norm` reintroduction:** Section 10 documents that
an early Phase 2 iteration removed these two spatial features after they
enabled severe location-memorization overfitting (training R²=0.980 vs.
held-out R²=0.20) under a much smaller training table and unconstrained
trees. v2 reintroduces them under materially different conditions: a
substantially larger, better-regularized training table (see Section 11),
HistGradientBoosting with `min_samples_leaf=20` and `l2_regularization=1.0`,
and — critically — a region-level holdout check (Section 12.4) run
specifically to test whether this reintroduction caused the same
memorization failure mode again. It did not eliminate the underlying
spatial-extrapolation weakness, but the mechanism is different from the
original 2020-training-R²-style overfitting; see Section 12.4 for the
actual, quantified result.

**Leakage safeguard for `target_lag1`:** this feature is sourced
exclusively from the training-well-derived Kriged surface directory, both
during training and during held-out validation. It never reads a held-out
well's own historical readings at any point, preserving the Section 3
anti-circularity boundary. Unchanged from v1. **Source-level verification
(session integration, this revision):** the exact guard was re-read
directly from `feature_utils.py` (lines ~358–445) and `rf_downscale.py`
(lines ~136–138) in a subsequent working session. The matching function,
`find_nearest_prior_kriged`, enforces `if file_month >= target_month:
continue` when scanning candidate Kriged surfaces for a given target date
— i.e. it explicitly skips any candidate surface whose month is not
strictly earlier than the target month before considering it as a
`target_lag1` match. This is the same safeguard the leakage
audit (Section 51.3 of the Phase 5 material below) reports
having independently confirmed at the source-code level; this note
records the specific function name and guard condition for direct
citation.

**Carried-forward bug fixes (still apply to v2 unchanged):**
- **Calendar-month vs. exact-day lag comparison bug**, fixed by comparing
 `(year, month)` tuples instead of raw dates.
- **Month-shift date arithmetic bug** (e.g. `2018-02-30` does not exist),

## 10. A Critical Overfitting Bug (Found, Diagnosed, and Fixed — v1)

An earlier version of the feature set included normalized grid position
(`row_norm`, `col_norm`) as explicit spatial features. Combined with a
severely reduced training date count (a side effect of the lag/rolling
requirements — as few as 7 usable dates in one iteration), this let the
Random Forest use location as a near-unique fingerprint for each specific
Kriged surface, memorizing rather than learning a generalizable
relationship: **training R² = 0.980, held-out R² = 0.20**, an
unusually large and suspicious gap. **Fix (v1):** `row_norm`/`col_norm`
were removed from the feature set, and the model was regularized
(`max_depth`, `min_samples_split`, `min_samples_leaf` constraints, rather
than default unconstrained trees). This is documented here rather than
omitted because the diagnostic process — recognizing an implausibly high
training R² as a symptom of overfitting rather than a success — is itself
part of the methodology's defensibility.

**Status as of v2:** as noted in Section 9, `row_norm`/`col_norm` were
later reintroduced under different training conditions. The region-level
holdout in Section 12.4 is the closest available check on whether this
reintroduction reproduces a spatial-memorization problem; it shows the v2
model's advantage over kriging-only disappears (and kriging-only wins in
3 of 4 quadrants) once entire regions are excluded from training, which is
consistent with at least a *partial* return of the pattern this section
originally diagnosed, even though it does not reproduce the extreme
training/held-out R² gap seen here. This should be read together with
Section 12.4, not in isolation.

## 11. Hyperparameter Selection and Model Comparison (Revised for v2)

**Principle (unchanged):** the held-out set must be touched at most once,
at the very end. All exploratory tuning uses training-data-only,
spatially-blocked cross-validation.

**Folding strategy — methodological correction (unchanged, carried
forward from v1):** an initial CV design grouped folds by **date**
(holding out entire time periods). This produced strongly negative R²
across every hyperparameter configuration tested, because it measures a
different, harder question than the one held-out well evaluation actually
answers — the held-out well split (Section 3) is *spatial*, not temporal,
so most held-out readings fall on dates the model already saw via other
training wells. **Corrected folding strategy:** spatial-block CV (an 8×8
tiling for v1; **16 blocks for v2**, see below), mixing all available
dates freely within each fold.

**v2 model comparison (spatial CV, training data, 139,264 rows, 16
blocks):**

| Candidate | Target mode | CV RMSE | CV R² |
|-----------|-------------|--------:|------:|
| hgbr_residual | residual | **1.828** | **0.612** |
| rf_depth | depth | 1.834 | 0.611 |
| hgbr_depth | depth | 1.860 | 0.599 |
| rf_residual | residual | 1.874 | 0.594 |

Spatial-CV selected `hgbr_residual`. **Held-out evaluation of all four
candidates (Section 12.3) later showed all four are within 0.035 m RMSE
of each other and statistically equivalent — the CV-selected model is not
meaningfully better than the alternatives; model family and target-mode
choice do not materially affect held-out skill.**

**11.1 Model and target configuration (v2, adopted):**
- Model family: `HistGradientBoostingRegressor`
- Target mode: **residual** — the regressor learns `(target − target_lag1)`
 and prediction reconstructs `pred = lag + Δ`. Compared against "depth"
 mode; the two were equivalent on held-out (Section 12.3).
- Hyperparameters: `max_iter=300`, `learning_rate=0.06`,
 `max_leaf_nodes=31`, `min_samples_leaf=20`, `l2_regularization=1.0`,
 random_state=42.

**11.2 Matching windows (v2):**
- Base covariate match window: 90 days; fallback window: 400 days
 (stale-composite recovery).
- Lag match window: 120 days; fallback: 365 days.

**Secondary finding, retained as an honest limitation (unchanged from
v1):** date-grouped CV, re-run as a documented diagnostic (not for
tuning), consistently shows negative R² across all configurations. The
model has not been shown to reliably extrapolate to genuinely unseen time
periods — it interpolates well spatially within the observed historical
record, but has not been shown to generalize to future dates outside it.

### 12.9 Comparison to published groundwater ML results

Placing the v2 RF downscaler in the published literature is complicated by
divergent evaluation protocols. Two facts dominate the comparison: our target
is the training-well Kriged surface (a smoothed interpolation, not raw
observations) and our holdout is well-level rather than spatially blocked
across regions. On the first, the target's smoothness limits achievable R²
regardless of model family (§1B.8); on the second, §12.4.2 shows directly
that under region-level holdout, kriging-only outperforms the RF in 3 of 4
quadrants (pooled R²=0.155 vs 0.101), indicating that the RF's within-region
advantage is interpolation between observed wells rather than a generalizable
learned relationship.

The papers closest in scope:

- **Nolan et al. (2015), J. Hydrology** — spatial cross-validation for
 groundwater ML; establishes that random KFold overstates skill relative to
 spatial holdout by roughly 2–3× in R². Our §12.4.2 region-holdout gap
 (0.187 held-out vs 0.50–0.64 spatial-CV) is consistent.
- **Ruybal et al. (2019), Water Resources Research** — regression kriging
 with a DEM covariate improves groundwater-level predictions at unmonitored
 locations. Our `--with_terrain` option is the equivalent feature in this
 pipeline (§9), not yet ablated.
- **Jyolsna & Kambhammettu (2021), Hydrological Sciences Journal** — RF
 downscaling of GRACE over India, R² ≈ 0.4–0.6 on a denser holdout than
 ours. Direct numerical comparison is not meaningful because target and
 holdout design differ.
- **Wang et al. (2024), J. Hydrology** — recent RF downscaling with a
 spatial holdout excluding whole regions; higher reported skill than ours
 and the reason is the holdout design.

**Honest position.** R²=0.187 is in the middle of published well-level
groundwater ML results once holdout design is accounted for. It is not
state-of-the-art. The contribution is not the numerical skill of the
downscaler — it is the end-to-end integration, the anti-circularity
discipline, and the documented failure modes. Any comparison table should
carry the caveat that the RF layer's skill is bounded above by the Kriged
target quality, and that any published result which does not disclose its
holdout design is not directly comparable.

**Comparison to published offline RL.** No directly comparable
offline-RL-for-groundwater-pumping paper is known. RL for water resources is
a growing but thinly populated niche; published work tends to focus on online
RL in reservoir operations rather than offline decision-support on a synthetic
groundwater simulator. The methodological comparison appropriate here is to
offline-RL evaluation practice: our use of both FQE and direct rollout, with
their documented disagreement (§36–37), is a standard sanity check; the
additional genuine-OOD test (§46.1) is more rigorous than the standard. The
finding that CQL's advantage reverses under OOD has no obvious published
precedent in the water-resources RL literature and is offered as a
methodological contribution in its own right.

## 12b. Phase 2.5 — Enhancement Tests (Both Rejected, Run Against v1)

**These two experiments were run against the v1 baseline (R²=0.198 /
0.189, as applicable) and have not been re-run against v2.** Retained here
as verified negative results and as the direct precedent for Phase 2.6's
pre-registration discipline (Section 20).

**Test 1 — Cumulative Rainfall Deficit.** Added `chirps_cum12_anomaly`
(12-month cumulative rainfall anomaly vs. climatology) to the v1 feature
set, following the same training-only CV-first discipline as every other
enhancement attempt. The feature was genuinely used by the model
(importance 0.052 in the retrained RF), but held-out R² came back at
**0.190** — below the v1 baseline of 0.198. **Rejected.**

**Test 2 — Residual Kriging.** A hybrid approach: fit RF as usual, then

surface as a correction. Initial cross-validation used a plain, random
`GroupKFold` (grouped by date) and showed a promising +0.041 CV gain —
but this used the same easier, date-grouped folding strategy Section 11
already diagnosed as measuring a different, easier question than the true
(spatial) held-out geometry. Re-run with the corrected spatially-blocked
CV, the gain shrank to only +0.006 — small enough that a held-out check
was borderline, but was run anyway as a documented decision point.
Held-out R² came back at **0.182**, below the 0.189 baseline used for
that specific comparison — worse, not better. **Rejected.**

**Why this matters for Phase 2.6's later discipline (Section 20):** Test
2's experience — a CV gain that looked real under an easier folding
scheme and evaporated under the correct one — is the direct precedent for
Phase 2.6's decision to require spatially-blocked CV *and* a
pre-registered improvement threshold (+0.02) before any further held-out
touch.

## 14. Grid-to-Grid ConvLSTM

### 14.1 Architecture Implemented

`src/models/convlstm.py` — a self-contained ConvLSTM cell implementation
(no external ConvLSTM library dependency, per the roadmap's explicit
requirement), verified against the roadmap's exact tensor-shape
specification via an automated smoke test:

- **Input:** `(batch, seq_len, channels, 64, 64)`
- **Output:** `(batch, 1, 64, 64)`
- **Cell design:** a single `Conv2d` producing all four LSTM gates
 (input, forget, output, candidate) at once from the concatenation of
 the current input and previous hidden state — standard ConvLSTM gating,
 substituting 2D convolutions for the fully-connected gates of a
 classical LSTM cell, to preserve spatial structure across the sequence.
- **Config-driven:** `hidden_dim`, `num_layers`, `kernel_size` read from
 `config/model_config.yaml`, supporting either a single scalar (applied
 to every layer) or a per-layer list.
- **Read-out head:** a `1×1` convolution collapsing the final layer's
 hidden state to a single-channel output grid.

### 14.2 Sequence Assembly Pipeline

`src/models/prepare_sequences.py` builds rolling windows over the Kriged
surface dates:

1. Loads all available Kriged target surfaces (`.npy` files in
 `data/interim/kriged_target_monthly/`).
2. For each date, builds the covariate stack via
 `build_feature_stack_for_date` (the same function used by
 `residual_kriging.py` in Phase 2.5) — channels: `chirps`, `gldas`,
 `sentinel2_ndvi`, `grace`, `srtm_elevation`, `srtm_slope`,
 `chirps_roll3`, `gldas_roll3`.
3. Slides a `SEQ_LEN`-quarter window across **consecutive** valid dates,
 rejecting any window whose internal gaps (or gap to its target date)
 exceed `MAX_GAP_DAYS`.

**Revision from monthly to quarterly framing:** the initial version
assumed monthly cadence (`SEQ_LEN=12`, implicit ~30-day gap tolerance).
Because CGWB campaigns are actually quarterly (Section 2), this was
revised to `SEQ_LEN=6` (six quarters ≈ 1.5 years) and `MAX_GAP_DAYS=120`
(allowing up to ~4-month gaps between consecutive quarters, matching
observed real campaign spacing per Section 9's lag-window finding for
Phase 2).

### 14.3 Root-Cause Diagnosis: Coverage Analysis (`check_coverage.py`)

The initial run under the revised quarterly framing produced only **7
usable training sequences** — an unexpectedly low count against 38 total
Kriged surfaces. Rather than treat this as an unexplained data problem,
a dedicated diagnostic script checked every one of the 38 Kriged dates
individually for covariate-stack completeness.

**Result: 25/38 dates have a usable stack; 13/38 fail outright** (stack
returns `None`, meaning at least one covariate source has zero coverage
for that date). Critically, the 25 usable dates are **not contiguous** —
they fall into five isolated runs:

| Run | Date range | Length (quarters) | Sequences contributed (seq_len=6) |
|---|---|---|---|
| A | 2015-08 → 2016-01 | 3 | 0 |
| B | 2016-05 → 2017-01 | 4 | 0 |
| C | 2017-05 → 2017-08 | 2 | 0 |
| **D** | **2018-05 → 2020-01** | **13** | **7** |
| E | 2020-08 → 2021-01 | 3 | 0 |

A run of length *L* contributes `max(L − seq_len, 0)` sequences. Only Run
D (13 quarters) exceeds the 7-quarter minimum (6 input + 1 target) needed
to contribute even one sequence — exactly reproducing the observed count
of 7.

**Per-channel attrition detail:** among the 25 "usable" dates, NaN
fraction varies sharply by channel. `sentinel2_ndvi` is the dominant
source of both hard failures and soft degradation, ranging from 10% to
**100%** NaN on individual dates (e.g. 2016-08-01, 2020-08-01) — far
higher and more erratic than any other channel. This is consistent with
Sentinel-2's known cloud-cover sensitivity, already documented as a
Phase 1 limitation (Section 4/Section 5), and is one contributing reason
Sentinel-2 was later dropped entirely from the v2 Phase 2 feature set
(Section 12.2).

**Gap-by-gap explanation:**

| Gap | Duration | Likely cause |
|---|---|---|
| 2013-01 → 2015-05 | ~2.5 years, near-total failure | Sentinel-2A launched June 2015 — imagery genuinely does not exist before this |
| 2017-11 → 2018-01 (and surrounding attrition through 2018-01) | ~2–3 months of failures | Plausibly linked to the documented GRACE mission transition gap (Jul 2017–Apr 2018, Section 4) |
| 2020-01 → 2020-08 | ~7 months | Plausibly COVID-19 field-campaign disruption — **not independently confirmed** against a CGWB campaign-schedule source; stated here as a plausible, not verified, explanation |

### 14.4 Training Attempt and Result

Given the severe sample-size constraint, a patch-augmentation strategy
(`patch_augment.py`) was tried before abandoning the grid approach
entirely: each 64×64 grid is cut into non-overlapping 16×16 spatial
patches, multiplying the number of training examples per real sequence
without claiming to create new independent information (documented
explicitly in the module's own docstring as a way to extract more
gradient signal from a small dataset, not a fix for the underlying
scarcity).

**Critical correctness safeguard:** the train/validation split was
performed at the **original sequence level first** (last 1 of 7
sequences reserved for validation), and patches were extracted
**separately** for each side afterward — never pooling all patches
together before splitting. This prevents patches from the same
underlying grid (which are spatially correlated, sharing the same date
and regional context) from leaking across the train/validation boundary.

**Configuration used:** `hidden_dim=8`, `num_layers=1` (deliberately
minimal, given the sample size), `patch_size=16` (stride = patch_size,
non-overlapping), batch size = 8, Adam optimizer (lr=1e-3,
weight_decay=1e-4), `SmoothL1Loss`, early stopping patience = 15.

**Data split:** 6 training sequences → 96 patches; 1 validation sequence
(2020-01-01) → 16 patches.

**Training curve (selected epochs):**

| Epoch | Train Loss | Val Loss |
|---|---|---|
| 10 | 25.362 | 19.507 |
| 20 | 18.200 | 13.816 |
| 30 | 13.921 | 10.863 |
| 40 | 11.583 | 9.695 |
| 50 | 9.762 | 14.372 |
| 55 (early stop) | — | 9.695 (best) |

**Final result:** validation R² = **−0.0655** (n=4,096 pixels, all drawn
from the single held-out sequence's 16 patches) — worse than predicting
the mean. Training loss continued to fall while validation loss began
rising after epoch ~40, a classic overfitting signature consistent with
having only 6 independent training examples regardless of patch count.

**Held-out CGWB well evaluation (Metric 2) was never computed for this
model.** Per the project's cross-validation discipline (Section 11), the
held-out set is touched only once a model has already demonstrated
viability on training-only validation. Since Metric 1 (against the
Kriged surface, the easier of the two required metrics) had already
failed decisively, running Metric 2 would have provided no additional
information and would have used up part of the project's held-out-touch
budget for no benefit.

### 14.5 Alternatives Considered and Rejected (Quantified)

Before abandoning the grid approach, shrinking `seq_len` was considered
as a way to admit Runs A/B/C/E into the training set. This was rejected
on quantitative grounds, computed directly from the run-length table in
Section 14.3:

| `seq_len` | Sequences from Run A (3) | Run B (4) | Run C (2) | Run D (13) | Run E (3) | **Total** |
|---|---|---|---|---|---|---|
| 6 (used) | 0 | 0 | 0 | 7 | 0 | **7** |
| 5 | 0 | 0 | 0 | 8 | 0 | **8** |
| 4 | 0 | 0 | 0 | 9 | 0 | **9** |
| 3 | 0 | 1 | 0 | 10 | 0 | **11** |
| 2 | 1 | 2 | 0 | 11 | 1 | **15** |

Even the most aggressive reduction tested (`seq_len=2`, which would also
weaken the model's temporal memory to just two quarters, undermining the
entire motivation for a sequence model over RF's single-lag feature) tops
out at an estimated 15 sequences — still one to two orders of magnitude
below what spatiotemporal deep learning typically requires for reliable
generalization. **This quantitative ceiling, not just the 7-sequence
result at `seq_len=6`, is the basis for treating grid-level ConvLSTM as
infeasible at the current data volume**, rather than a problem `seq_len`
tuning could solve.

Two further alternatives were identified but not implemented:
- **Relaxing `sentinel2_ndvi`'s completeness requirement** — could
 recover some hard-failure dates, but would not bridge the genuine,
 multi-month structural gaps (Sentinel-2 pre-launch, the GRACE
 transition, the 2020 gap), which are the dominant constraint on run
 length, not per-date NDVI noise.
- **Extending the historical covariate pull** — would not help, since the
 binding constraint is *contiguous* coverage, not total date count, and
 the existing record already spans the full CGWB data availability
 window (Section 2).

### 14.6 Decision

Grid-to-grid ConvLSTM was **not pursued further**. This is documented as
a structural, data-availability finding — a property of the underlying
satellite/campaign coverage record, independently diagnosed and
quantified rather than assumed — not a code defect, an architecture
choice, or a tuning failure. The project pivoted to a point-scale
architecture (Section 15) that does not require whole-grid temporal
contiguity. Full practical implications and downstream recommendations
are recorded in `reports/limitations.md`, Section 5.

## 15. Point-Scale (Per-Well) LSTM: Revised Methodology

### 15.1 Rationale

The constraint diagnosed in Section 14 is specific to *grid-level*
sequences, which require an unbroken run of fully-covered calendar
quarters across the **entire study region simultaneously**. A
*well-level* sequence only requires covariate coverage at **one well's
single pixel** for each of that well's own reading dates — a
categorically weaker requirement. Isolated "OK" dates that could not
support a grid-wide sequence (Runs A, B, C, E — 12 of the 25 usable
dates, 48% of usable coverage) still contribute usable rows at the well
level, since each well-date row is evaluated independently rather than
requiring simultaneous region-wide coverage.

This also better matches the data granularity that made Phase 2's RF
model viable in the first place: RF trained on independent (grid-cell,
date) samples, not full-grid snapshots. The point-scale LSTM restores
that same granularity while adding sequential memory RF's single
`target_lag1` feature could not capture.

### 15.2 Data Preparation Pipeline (`build_well_level_dataset.py`)

For every well reading — built as two **separate** invocations, one for
the training-well set and one for the held-out-well set, preserving the
Section 3 spatial split exactly rather than re-deriving it — the script:

1. Groups readings by their exact date to avoid rebuilding the same
 covariate stack redundantly (cache pattern, same as
 `compute_rf_predictions_at_wells` in Phase 2.5).
2. Samples the covariate stack (`build_feature_stack_for_date`,
 `kriged_dir` passed through for the `target_lag1`-equivalent signal)
 at the well's exact grid cell via `latlon_to_grid_cell`.
3. Retains the row unless **every** channel is NaN at that pixel — a
 single noisy channel (typically `sentinel2_ndvi`) does not disqualify
 an otherwise-usable reading, unlike the grid pipeline's stricter
 whole-stack requirement.
4. Joins the resulting feature vector with the well's own raw `depth_m`
 reading.

**Output granularity:** one row per (well, date) — matching Phase 2 RF's
training granularity exactly (at v1 time).

**Coverage result (held-out set):** of 16,073 held-out readings, **8,127
rows (50.6%) retained a usable sample** — 7,946 skipped for having no
covariate stack at all on their date. This is consistent with (and
somewhat better than) the ~66% date-level unusability found in Section
14.3, since the well-level pipeline's per-channel tolerance recovers
some rows that the grid pipeline's all-channels-complete requirement
would have discarded.

### 15.3 Model Architecture (`train_point_lstm.py`, `WellLSTM`)

- **Sequence input:** a 2-layer LSTM (`hidden_size=64`, `dropout=0.2`)
 over six time-varying covariates: `chirps`, `gldas`, `sentinel2_ndvi`,
 `grace`, `chirps_roll3`, `gldas_roll3`.
- **Static input:** two terrain covariates constant per well —
 `srtm_elevation`, `srtm_slope` — concatenated with the LSTM's final
 hidden state.
- **Output head:** `Linear(66 → 32) → ReLU → Dropout(0.2) → Linear(32 → 1)`,
 predicting a scalar delta.
- **Target formulation — delta, not absolute depth:** the model predicts
 `next_depth − last_known_depth`, reconstructing the absolute prediction
 by adding this delta back to the well's own true previous reading. This
 design choice was made specifically in response to the depth-dependent
 compression bias diagnosed for the v1 RF model (`limitations.md`,
 Section 1), where RF's leaf-averaging structurally shrank predictions
 toward the training distribution's center, especially at depth.
 Starting from the well's own true anchor point removes the need for the
 model to reconstruct absolute level from covariates alone — it only has
 to predict the *change*, a narrower and better-conditioned target.

### 15.4 Training Configuration

| Hyperparameter | Value |
|---|---|
| Sequence length (`seq_len`) | 4 quarters |
| Optimizer | Adam, lr=1e-3, weight_decay=1e-5 |
| Loss function | `SmoothL1Loss` (Huber-style; more robust to depth outliers than plain MSE) |
| Batch size | 128 |
| Max epochs | 80 |
| Early stopping patience | 10 epochs (on validation loss) |
| Train/val well split | 85% / 15%, by well ID |

**`seq_len=4` rationale:** chosen as a practical default after the grid
model's 6-quarter (and even 2-quarter, per Section 14.5's table) lookback
proved infeasible at the grid level. **Not separately tuned** against
alternative lengths (2, 3, 5, 6) as of this writing — see Section 18,
open items.

### 15.5 Anti-Leakage Safeguards

- **Spatial split reuse, not re-derivation:** sequences are built
 independently per well, and the training/held-out well partition reuses
 the exact Section 3 spatial split rather than performing any new
 splitting logic that could silently diverge from the project's single
 canonical held-out set.
- **Normalization fit boundary:** feature normalization (`StandardScaler`,
 per-channel, fit via `fillna(column mean)` before fitting to avoid
 NaN-propagation into the scaler) is fit on **training wells only** and
 applied unchanged to both the internal validation split and the true
 held-out set — no statistics from held-out data ever influence scaling.
- **Sequence-level well grouping:** within a well, sequences are built
 from that well's own chronologically-sorted readings only; no
 cross-well sequence mixing occurs at any point.
- **Internal validation split (85/15, by well ID)** provides an
 early-stopping signal without touching the true held-out wells,
 mirroring the same discipline as Phase 2's training-only
 cross-validation (Section 11).

## 16. Point-Scale LSTM: Final Held-Out Validation Result

Evaluated once against the true held-out CGWB wells
(`train_point_lstm.py`'s printed headline metric, independently confirmed
with well_id/date metadata attached via `eval_point_lstm.py`).

### 16.1 Headline Comparison Table

**See the cross-reference note at the top of Phase 3: the RF row below
uses the v1 Phase 2 number, not the current v2 number from Section 12.**

| Model | Task | R² | RMSE (m) | MAE (m) | N |
|---|---|---|---|---|---|
| RF (Phase 2, **v1**) | Spatial downscaling — any location, including unmonitored | 0.198 | 5.226 | 3.371 | 4,869 |
| Naive persistence | Predict next reading = last reading, at monitored wells only | 0.439 | 4.283 | 2.500 | 5,597 |
| **Point-scale LSTM** | Forecast next reading from covariates + history, at monitored wells only | **0.575** | **3.726** | **2.023** | 5,597 |

### 16.2 Framing Caveats (Critical — Do Not Omit When Citing This Result)

**(a) Task-scope mismatch with RF.** RF solves a structurally harder
problem: predicting groundwater depth at *any* location, including places
with no well history at all. Its R² must be read in that context — not as
an inferior version of the task the LSTM solves. Conversely, the
point-scale LSTM **cannot** answer "what is the depth at this unmonitored
location?" — only "given this well's own history, what will it read
next?" The two are complementary results, not directly substitutable, and
should never be presented as a simple "LSTM beats RF" claim.

**(b) Persistence, not RF, is the valid baseline for isolating the LSTM's
learned contribution.** Because the delta-target design gives the LSTM
access to the same anchor information a naive persistence baseline uses
(the well's own last true reading), a meaningful share of its apparent
skill could, in principle, be pure autocorrelation rather than learned
dynamics. The dedicated persistence check
(`persistence_baseline_check.py`, run on the identical held-out
sequences) shows persistence alone reaches R²=0.439. The LSTM's
defensible, reportable contribution is the **gap above persistence**:

| Metric | Persistence | LSTM | Improvement |
|---|---|---|---|
| R² | 0.439 | 0.575 | +0.136 absolute (24.2% reduction in remaining/unexplained variance: (1−0.439) → (1−0.575)) |
| RMSE (m) | 4.283 | 3.726 | −13.0% |
| MAE (m) | 2.500 | 2.023 | −19.1% |

This gap — not the raw R²=0.575 figure in isolation — is the number that
represents genuinely learned, covariate-driven predictive skill beyond
what quarter-to-quarter groundwater persistence already provides for
free.

**(c) Consistency with Phase 2's own feature importances (v1).** v1's
final model already ranked `target_lag1` as its second-largest
contributor (0.247, essentially tied with `grace` at 0.253) using only a
*single* prior reading as a feature, with no sequential structure. The
point-scale LSTM's result is consistent with, and quantitatively extends,
that earlier finding: temporal memory is a real and substantial source of
signal for this problem, and a sequence model can extract more of it than
a single-lag feature can.

### 16.3 Held-Out Coverage for This Evaluation

Of 710 held-out wells, 609 (85.8%) retained enough surviving readings
(> `seq_len`=4, after the coverage attrition described in Section 15.2)
to contribute at least one evaluation sequence, yielding 5,597 evaluable
sequences from those wells. The other 101 wells were excluded from Phase
3 evaluation entirely. This evaluated subset should not be assumed
representative of all 710 held-out wells uniformly.

### 16.4 Conclusion

The point-scale LSTM should be reported as a **complementary result** to
the RF baseline, not a replacement for it: RF provides the spatial
coverage the project's original downscaling objective requires; the
point-scale LSTM provides a well-scoped, honestly-caveated demonstration
that temporal memory carries real, learnable predictive signal beyond
what a static, single-lag regression model can extract.

## 17. Bugs Found and Fixed During Phase 3

**Import path mismatch (`ModuleNotFoundError: feature_utils`).** Multiple
Phase 3 scripts (`prepare_sequences.py`, `eval_convlstm.py`) initially
inserted `src/data/` onto `sys.path` when importing `feature_utils`,
following an assumption from the roadmap's repository layout. In the
actual implemented repository, `feature_utils.py` resides in
`src/downscaling/` (alongside `rf_downscale.py`, which depends on it).
Fixed by aligning every Phase 3 script's `sys.path` insertion with the
pattern already working in `residual_kriging.py`
(`parent.parent / "downscaling"`).

**`ConvLSTM.__init__` crash on list-valued `kernel_size`
(`TypeError: unsupported operand type(s) for //: 'list' and 'int'`).**
The original architecture only normalized `hidden_dim` to a per-layer
list, not `kernel_size`; a `model_config.yaml` specifying `kernel_size` as
a per-layer list (mirroring `hidden_dim`'s own list format) reached
`ConvLSTMCell.__init__` unnormalized, where `kernel_size // 2` fails
against a list. Identified during the first `train_convlstm.py` run,
before any training compute was spent past model construction.

**Patch-level train/validation leakage risk (identified and designed
against proactively, not caught as a live bug).** Because patch
augmentation (Section 14.4) extracts multiple spatially-correlated
patches from each original sequence, splitting patches directly (rather
than splitting whole sequences first) could have let validation patches
sit immediately adjacent to training patches from the same date/region —
a spatial-leakage pattern directly analogous to the `GroupKFold` issue
found and fixed in Phase 2.5's residual-Kriging cross-validation.
`patch_augment.py` and the patched training script were written with the
sequence-level split enforced *before* patch extraction specifically to
avoid reintroducing this same failure mode in a new form.

## 19. Proposed Future Covariate: Static Hydrogeological Variables

**Question raised:** would adding static hydrogeological covariates
(geology/lithology, soil type, land use/land cover) improve accuracy
beyond the current terrain covariates (`srtm_elevation`, `srtm_slope`)?

### 19.1 Why This Is a Physically Sound Direction

Groundwater depth is fundamentally controlled by the aquifer material it
sits in, not just surface topography. The current feature set captures
*surface* signals (rainfall, soil moisture, vegetation, elevation/slope)
and *temporal persistence* (`target_lag1`), but has no direct
representation of **why** two locations with similar rainfall and
elevation can have very different groundwater depths — which is
substantially explained by underlying rock type. Specifically:

- **Lithology/geology** (e.g. basalt vs. alluvium vs. crystalline
 basement rock) governs porosity and permeability, directly controlling
 how much water an aquifer can store and how fast it recharges. Much of
 Maharashtra sits on Deccan Trap basalt, a fractured-rock aquifer system
 that behaves very differently from the alluvial aquifers common
 elsewhere in India — this single distinction plausibly explains part of
 the spatial variance the current model treats as unexplained noise.
- **Soil type** affects infiltration rate — a variable the current
 `chirps`/`chirps_roll3` features assume is spatially uniform, which it
 is not.
- **Land use/land cover** affects both recharge and extraction pressure —
 a demand-side signal the current feature set has no equivalent for at
 all.

### 19.2 Practical Considerations Before Implementing

- **Data source:** would require a new static raster source, comparable
 in scope to the original SRTM pull (Section 7), not a quick
 feature-engineering addition.
- **Static, like SRTM:** these variables would integrate the same way
 `srtm_elevation`/`srtm_slope` currently do. Categorical variables would
 need one-hot or target encoding.
- **Anti-leakage discipline unaffected:** static, location-only
 covariates introduce no new circularity risk.
- **Where to test it first:** the RF spatial downscaling model, since
 that is the model whose actual purpose is predicting at unmonitored
 locations, where surface-only covariates are weakest.
- **Testing protocol:** add the feature, re-run training-only,
 spatially-blocked cross-validation, and only proceed to a held-out
 check if the CV result shows genuine improvement — exactly the pattern
 used in Phase 2.5 and Phase 2.6.

### 19.3 Assessment

**This is a legitimate, well-motivated direction for future work, not yet
implemented.** Given that RF's depth-compression bias (v1;
`limitations.md` Section 1) stems partly from class imbalance in the
training target's depth distribution, a hydrogeology covariate would not
by itself fix that structural issue, but could plausibly reduce the
*baseline* error before that compression effect is applied.

# Phase 4 — Synthetic Offline RL Dataset Generation

## 21. Design Decisions (Spatial/Temporal Unit)

Two design decisions were fixed before writing any simulator code:

**Decision-space unit: reuse the 8×8 spatial block tiling** originally
defined in `cv_tune.py`'s `assign_spatial_block()` (Section 11), not
individual 64×64 grid cells and not a single region-wide policy. This
avoids introducing a second, inconsistent spatial partitioning scheme
alongside the one already used for RF's cross-validation.

**Time step: one CGWB campaign quarter**, matching the cadence used
throughout Phases 1–3.

State, action, and reward are defined per (spatial_block, quarter).
**Open item:** the actual implementation (`src/utils/spatial_block_cv.py`,
imported by `generate_offline_dataset.py`) re-implements this partition
with a different function signature (`assign_spatial_block(lat, lon,
bbox, n_grid)`) than `cv_tune.py`'s original (`assign_spatial_block(row,
col, grid_size)`). The code comments assert this reuses "the same"
partition, but this has not been independently verified — see Section 28.

## 22. State Space (as implemented)

The implemented state (`synthetic_reward.py`'s `SimState` dataclass) has
six fields:

| Field | Meaning | Source |
|---|---|---|
| `gw_level` | Depth to water, meters below ground (larger = deeper = worse, consistent with `currentlevel` throughout this project) | Seeded from real RF predictions (Section 25); evolves via the simulator thereafter |
| `recent_rainfall` | mm, 3-month rolling proxy | Seeded from real CHIRPS `chirps_roll3` values; evolves via a crude AR(1)-ish random drift thereafter (`synthetic_reward.step()`) |
| `crop_water_demand` | 0–1 normalized synthetic demand proxy | **A1** — synthetic, not derived from real crop-water-requirement data (see Section 24) |
| `month_sin`, `month_cos` | Cyclical calendar encoding | Advanced explicitly by the trajectory generator each quarter (`generate_trajectory()`); the simulator's own `step()` does not advance these |
| `extraction_rate` | 0–1 normalized recent pumping intensity | Endogenous; exponentially-weighted rolling function of the simulator's own past actions |

## 23. Action Space

Unchanged from the original design: **5 discrete pumping levels (0–4)**,
applied per spatial block per quarter. `n_actions=5` is read from
`config/rl_config.yaml`'s `action_space.n_actions`.

## 24. Reward Function and Simulator Dynamics (`synthetic_reward.py`)

**Explicit framing, restated from the module's own docstring: this is a
SYNTHETIC ground-truth layer, separate from and additional to the
anti-circularity discipline applied to GRACE/CGWB data (Section 3). No
amount of RL training rigor makes the reward function itself "true."**

### 24.1 Numbered Assumption Log (as implemented, for direct citation)

- **A1.** `crop_water_demand` is a simple seasonal proxy (higher in
 pre-monsoon/summer months), not derived from actual crop-type maps,
 irrigation records, or FAO crop-coefficient tables.
- **A2.** `crop_revenue_proxy` assumes revenue rises with pumping only up
 to the point demand is met, then flattens — no real price/yield data
 backs the specific proxy formula's magnitude.
- **A3.** `domestic_supply_score` assumes a single, location-independent
 critical depth below which domestic access is considered compromised.
 Real adequacy depends on well depth, pump capacity, and local
 infrastructure, none of which is modeled.
- **A4.** `depletion_penalty` uses a single `sustainability_threshold_m`
 for the entire study region (`config/rl_config.yaml`). Real sustainable
 yield varies by aquifer type and geology (Section 19's untested
 hydrogeology direction) — a simplification, not a validated threshold.
- **A5.** The action→`gw_level` relationship is a simple linear-plus-
 recharge model, not a calibrated aquifer response function.
- **A6.** Recharge from rainfall is a fixed fraction of
 `recent_rainfall`, not a physically calibrated infiltration model.
 **A partial behavioral validation of this assumption's qualitative
 direction against real CGWB observations is reported in Section 55
 below.**

### 24.2 State Transition (`step()`)

```
drawdown = pumping_fraction * 2.0 # up to 2m/quarter at max pumping (A5)
recharge = 0.15 * recent_rainfall / 100 # crude mm->m fraction (A6)
next_gw_level = max(0, gw_level + drawdown - recharge + noise)
```

`crop_water_demand` evolves via `clip(demand + N(0, 0.05), 0, 1)` — pure
noise, **not re-derived from the advancing month**. A1's seasonal pattern
only genuinely holds at a trajectory's first step; every subsequent
quarter, demand drifts randomly rather than tracking the (correctly
advancing) `month_sin`/`month_cos` fields.

### 24.3 Reward Components

```
reward = w1_crop_revenue * crop_revenue_proxy(action, demand)
 + w3_domestic_supply * domestic_supply_score(next_gw_level)
 - w2_depletion_penalty * depletion_penalty(next_gw_level, threshold)
```

All weights and thresholds are read from `config/rl_config.yaml`'s
`reward` section, not hardcoded. **The expanded Phase 5 report's
reward-weight ablation (new Section 51 below) varies exactly these
`(w1, w2, w3)` weights, with the canonical configuration `(1, 2, 0.5)`.**

## 25. RF Seed Table (`build_rf_seed_table.py`)

Runs the trained RF model across **every grid cell, for every available
covariate date**, producing a full `(grid_cell, date)` prediction table.
Output: `reports/rf_grid_predictions.csv`.

**Model version used to seed Phase 4 — resolved (end-of-session integration).** This table was built from `data/processed/rf_downscale_model.joblib`. Direct artifact inspection confirms its identity: `joblib.load(...).n_features_in_ == 11`, matching v1's 11-feature `FEATURE_COLUMNS` exactly (Section 9). The parallel `rf_v2_noS2_model.joblib` has `n_features_in_ == 16` (v2). **Phase 4 is confirmed seeded from v1, not v2 — this is now verified rather than inferred.** Whether re-seeding from v2 would change Phase 5's results remains untested and stays a future-work item. The "61,913 groundwater-grid prediction rows" figure referenced in the expanded report matches `rf_training_table.csv` exactly — see §47.1.

## 26. Offline Dataset Generation (`generate_offline_dataset.py`)

Three distinct, individually-motivated behavior policies:

| Policy | Behavior |
|---|---|
| `random` | Uniform random action each step |
| `greedy_extraction` | Pumps to meet `crop_water_demand` exactly, ignoring depletion risk — deliberately unsustainable, to give the dataset real examples of heavy-extraction outcomes |
| `conservative` | Cuts to zero pumping once `gw_level` nears 80% of `sustainability_threshold_m`; otherwise pumps moderately (capped at 50% demand) |

`n_trajectories_per_policy` and `trajectory_length` are read from
`config/rl_config.yaml`'s `simulation` section. Initial states are seeded
from real data where possible (Section 25's table for `gw_level` and
`recent_rainfall`), sampled via **spatial-block stratification**.

Output format: `d3rlpy.dataset.MDPDataset`, with a graceful fallback to
raw `.npz` arrays if `d3rlpy` is not installed at generation time.

## 27. Offline Dataset Validation (`validate_offline_dataset.py`)

Nine automated checks: NaN/Inf sanity, state-value range checks,
action-distribution balance, reward non-degeneracy, duplicate-transition
rate, next-state responsiveness to action, monotonic pumping→drawdown,
rainfall→recharge direction, and reward variation across actions.

**Bug found and fixed (in the validator, not the generator).** The first
version of this script assumed the wrong sign convention for two checks
because it treated `gw_level` as if larger meant "better," when it is
actually depth-below-ground (larger = deeper = worse). Corrected both the
drawdown check and the rainfall check accordingly. **The underlying
numbers were identical before and after the fix — only the validator's
interpretation changed.**

**Independent confirmation, out-of-band.** A direct Pearson correlation
between rainfall and subsequent `gw_level` change, computed straight from
the raw HDF5 arrays, confirmed the corrected sign: **r = −0.13** — correct
direction, but weak, quantifying exactly how crude A6's fixed-fraction
model is. **This is a simulator-internal check (simulated rainfall vs.
simulated next-state change); it is distinct from, and should not be
confused with, the simulator-vs-real-CGWB behavioral comparison reported
in Section 55 below.**

## 30. Objective and Pipeline

be learned from the Phase 4 synthetic offline dataset, and specifically

over a **Behavioral Cloning (BC)** baseline on that same dataset.

**Completed pipeline:**

```
Phase 4 offline dataset → BC baseline → CQL training → CQL α sweep

 diagnostics → convergence/target-update diagnostics
```

All training operates on the static Phase 4 offline dataset. Policy

> "On the ε direct-rollout evaluation, CQL outperformed BC by 0.1096

## 38. Distribution-Shift / Support Diagnostics

A dedicated diagnostic compared the offline dataset's action distribution
against both the BC and CQL learned-policy action distributions, to check
whether either policy selects actions poorly represented in the dataset
it was trained on — a known failure mode in offline RL, since a policy's
value estimate is least trustworthy for actions the training data barely
covers.

**Action support in the training data (recap of Section 31):** heavily
skewed toward low-pumping actions — 0% and 25% pumping together account
for 60.8% of all transitions (8,417 + 9,820 of 30,000), while 100%
pumping accounts for only 8.3% (2,478 transitions). 100% pumping is the
least-represented action in the dataset, and any policy that leans on
it carries the least evaluation support of any of the five actions.

This diagnostic was run and completed; the resulting per-policy action
distributions have not been recorded in this document (Section 42, open
items).

## 39. CQL Training Stability / Convergence Diagnostics

An extended training/convergence investigation examined BC and CQL
Q-value/return behavior across target-network update windows over an
extended training schedule.

**Result, stated conservatively:** training curves showed movement toward
convergence, but not a clean, unequivocal convergence advantage for CQL
over BC.

### 39.1 Target-Update-Interval Investigation

The selected configuration uses a target update interval of 8,000
(Section 34.2). A diagnostic comparison against alternatives (500, 2,000,
4,000) examined whether this choice materially affects training dynamics.

**Result:** changing the schedule visibly altered the training
trajectory, but the diagnostic did not produce evidence sufficient to
overturn the 8,000 default. This is recorded as a diagnostic result (the
choice was checked, not merely assumed), not as a claim that 8,000 was
proven optimal via a formal sweep-and-select procedure comparable to
Section 35.

**Related finding from the target-update ablation (this session):** QR
critics at `target_update_interval=500` exhibited severe TD-loss
escalation (4.4 → 30.0 over 4 epochs across three seeds). Mean-Q critics
remained stable at both 500 and 8,000. This ablation is not itself a
Phase 5 result, but it is the reason the 8,000 default was not replaced
with a lower value.

## 41. Final Phase 5 Result and Conclusion

**What Phase 5 demonstrated:**

- A BC baseline was trained and evaluated against the three named
 behavior policies, with the Conservative policy the strongest baseline
 in every configuration.
- CQL was trained on the same offline dataset.
- An explicit α sweep was performed (Section 35); α=1.0 was set manually
 via `--alpha` flag, not selected by that sweep.
- FQE was used as one of two policy-value estimation methods.
- Direct simulator rollout was used as the second method.
- The two methods disagree on the ε configuration: direct rollout shows
 a significant CQL advantage (+0.1096, CI [+0.050, +0.174]), FQE shows
 a tie (−0.0018, CI [−0.042, +0.039]).
- Distribution-shift/support, training-convergence, and multi-seed
 diagnostics were completed.

**What Phase 5 did not demonstrate:**

- Consistent, method-independent superiority of CQL over BC.
- Any online, real-world, or real-simulator-interaction superiority of
 either policy beyond the ε direct-rollout result above.
- Real-world pumping-policy superiority, real-world aquifer improvement,
 or any causal groundwater-management benefit.
- Deployment safety of either learned policy.
- Long-term real-world aquifer sustainability under either policy.
- **(New) A CQL advantage that survives genuine state-distribution OOD —
 see Section 46.1 below, which found the advantage reverses.**

**Defensible summary statement for this phase:**

> An offline reinforcement-learning framework was implemented and
> evaluated for groundwater pumping advisory using a 30,000-transition
> offline dataset (Phase 4). Behavioral Cloning and Conservative
> Q-Learning were trained, CQL's conservatism hyperparameter was set to
> α=1.0 via manual override, and policy values were estimated using both
> Fitted Q Evaluation and direct simulator rollout. On the ε
> configuration, direct rollout showed a statistically significant CQL
> advantage over BC (+0.1096, 95% CI [+0.050, +0.174]), while FQE on the
> same trained policies returned a statistical tie (−0.0018, 95% CI
> [−0.042, +0.039]). The discrepancy between the two methods is
> unresolved. The no_oracle α variants produced confidence intervals
> that all contained zero. α-selection provenance and per-policy action
> distributions remain open (Section 42); per-seed numeric results are
> transcribed in ?40.

**This is the complete, defensible Phase 5 result and should be quoted at
this level of caveat — not simplified to "CQL beat BC" or "CQL did not
beat BC" — anywhere it is cited.**

**Provenance and scope of this section, restated:** everything below (new

larger Phase 5 report. Per the reconciliation note at the top of this

### 43.0 Contribution framing

The contribution of this work is not a state-of-the-art groundwater
predictor, nor a new offline-RL algorithm, nor a claim that RL can optimize
real-world pumping. It is a reproducible, fully auditable pipeline whose
behavior is characterized end to end — from satellite-derived groundwater
estimation through spatial holdout validation, synthetic environment
construction, and offline-RL policy evaluation. Four specific contributions
are documented:

1. **Anti-circularity discipline.** A held-out-well split (17.5% of CGWB
 wells, 710 of 4,063) that never touches Kriging, RF training, or model
 selection; enforced by automated assertion and a dedicated regression
 test suite.

2. **Characterized depth-stratification failure.** The RF downscaler's
 prediction error grows monotonically with depth (−5 m at 10–20 m,
 −27 m at 30–50 m, −61 m at 50+ m in the v2 model). A training-side
 mitigation (depth-balanced sample weighting) was tested and rejected:
 it degraded every aggregate metric without improving the deep bins.
 The failure is structural to the covariate set, not a loss-function
 or model-selection problem.

3. **Behavioral validation of a synthetic simulator.** The
 rainfall–groundwater response direction in the Phase 4 simulator
 matches the sign observed in real CGWB wells (r_obs = −0.325,
 r_sim = −0.117); the magnitudes are of broadly comparable order.
 A6's specific functional form is not calibrated — this is stated as
 a limitation.

4. **Offline-RL evaluation disagreement preserved as a finding.** Direct
 simulator rollout shows a significant CQL advantage over BC
 (+0.11, 95% CI [+0.05, +0.17]); FQE on the same trained policies
 returns a statistical tie (−0.002, 95% CI [−0.042, +0.039]). The
 discrepancy is reported rather than resolved. A genuine
 state-distribution OOD diagnostic (§46.1) further shows the CQL
 advantage reverses outside the training-state distribution
 (Δ = −16 to −38 return units), stated as a boundary condition on
 the method rather than smoothed over.

The paper's claims are therefore bounded: an offline RL policy can be
trained to outperform a behavior-cloning baseline **within the
training-state distribution** under a synthetic simulator whose groundwater
dynamics have been behaviorally validated against observed wells, and its
advantage does **not** extend outside that distribution. Any use of this
pipeline for real-world advisory would require calibrating the simulator's
action→drawdown relationship against historical pumping records, which is
not available in the study region at the required resolution.

**Research question (as stated in the expanded report):** can CQL learn a
groundwater-pumping advisory policy with higher long-term simulated
return than BC, when both learn from the same fixed offline dataset?

### 46.1 [New, session integration] Genuine State-Distribution OOD — Action and Return

**Provenance:** this diagnostic was constructed in a subsequent working
session specifically to supply the genuine out-of-distribution test that
the experiment above (Section 46) is named for but does not perform (its
own OOD fraction is 0.0). It is cross-referenced from `limitations.md`,
new Section 19.5, which carries the full narrative interpretation; this
section records the methodology and figures for the validation-record
audience.

**Construction:** four bands were built using Mahalanobis distance from
the training-state distribution's mean and covariance (computed over the
Phase 4 training-state array): an in-distribution (ID) band and three
progressively further-out bands, up to a "severe OOD" band. The same
canonical checkpoints (α=1.0, QR critic, Section 43) and the same three
seeds (42, 123, 2024) used throughout the expanded report were evaluated
against all four bands under a fixed, clean 20-step rollout horizon — the
fixed horizon was used specifically to prevent a confound where one
policy's episodes terminate earlier or later than the other's inside a
given band.

**Result — action distributions:** total-variation distance between the
BC and CQL action distributions stayed roughly stable across all four
bands (TV ≈ 0.62–0.65), i.e. the two policies' choice of action does not
diverge substantially further as states move away from the training
distribution.

**Result — return:** the return comparison, in contrast, moves
substantially and in the CQL-unfavorable direction as the band moves
further from the training distribution:

| Band | CQL − BC (return) |
|---|---|
| In-distribution (ID) | −16.01 |
| Severe OOD | −38.40 |

This is a **sign reversal** relative to every CQL-favorable return result
reported in Sections 44–45 and 47–50 (all in-distribution, fixed-scenario
comparisons) — under genuine OOD, BC outperforms CQL, and by a growing
margin as the distance from the training distribution increases.

**Interpretation:** CQL's conservatism penalty is defined over the
offline dataset's *action* distribution (Section 17 of `limitations.md`),
not its *state* distribution, so nothing in CQL's training objective
specifically protects it once the *state* itself is unfamiliar. The
action-distribution stability result above suggests the two policies do
not fundamentally disagree more about what to do as states move
out-of-distribution — but CQL's Q-value estimates for its chosen actions
in those unfamiliar states appear to be less reliable than BC's more
direct behavioral match, resulting in worse realized return. This is
offered as a plausible mechanism, consistent with the data, not as an
independently isolated causal finding — no ablation specifically
targeting the Q-function's OOD extrapolation behavior (e.g. an OOD-state
penalty term, or an ensemble-disagreement-based uncertainty bonus) has
been run to confirm it.

**Scope and relationship to other sections:** this diagnostic is
distinct from, and should not be conflated with, Section 46's
scenario-shift experiment above — that experiment varies transition and
reward *parameters* (drought/extreme rainfall) while remaining, by its
own reported OOD fraction, entirely in-distribution in state space; this
diagnostic varies the *state* directly and deliberately reaches
out-of-distribution. The two are complementary, not redundant, and reach
opposite qualitative conclusions about CQL's robustness because they
test different kinds of shift.

**Mean-Q replication (end-of-session integration).** The four-band diagnostic was repeated against a Mean-Q CQL critic (`reports/paper_exp/cql_mean/`, `qfunc="mean"`, canonical hyperparameters otherwise) with every other setting held fixed — same bands, same 200 states per band, same fixed 20-step horizon, same three seeds, same eval RNG. Results:

| Band | QR critic | Mean-Q critic |
|---|---|---|
| in-distribution | −16.01 | −8.64 |
| mild | — | −13.63 |
| moderate | — | −15.76 |
| severe OOD | −38.40 | −18.17 |

Both critics show CQL−BC return **negative in every band**, worsening monotonically from in-distribution to severe OOD. **The reversal is not QR-specific.** Magnitude roughly halves under Mean-Q: effect size is critic-dependent; the qualitative finding is critic-independent. A per-step termination diagnostic confirmed **20.00 mean steps and 0.000 terminated fraction** across all 24 policy×band cells, ruling out an early-termination confound in the fixed-horizon comparison. **Open item (i) closed.**

**Open items (remaining):** (ii) the four Mahalanobis bands have not been cross-referenced against which specific `SimState` fields drive membership in the most severe band; (iii) the diagnostic has been run once per critic formulation, on the same three seeds (42, 123, 2024) as every other Phase-5 robustness check (§40).

## 49. Expanded Report: QR vs. Mean-Q Critic — Not Established as Superior

**Finding:** the canonical CQL configuration uses a 32-quantile QR critic
(confirmed by direct checkpoint inspection: `QRQFunctionFactory
(n_quantiles=32)`). A dedicated ablation against a Mean-Q critic found QR
significantly outperformed Mean-Q on 2 of 3 seeds; on the third seed
(42), Mean-Q was numerically higher but the CI crossed zero.

**Practical implication:** the report's own conclusion — that QR
superiority is "promising but seed-sensitive" and not universally
established — is the correct, defensible framing and is retained
verbatim in spirit here. Given that all of Phase 5's robustness evidence
(both reports) is limited to exactly these same three seeds (Section 23
above), the QR-vs-Mean-Q result should be treated with the same
seed-count caution as every other three-seed claim in this document,
**including the new OOD diagnostic in Section 46.1, which has not been
repeated with a Mean-Q critic and so cannot rule out the critic
formulation as a contributing factor in the OOD reversal.**

## 50. Expanded Report: Scenario-Specific Adaptation Can Be Harmful

**Finding:** a frozen (normal-condition-trained) policy substantially
outperformed a scenario-specifically-retrained policy at 25 m
groundwater depth, across all three environmental conditions tested
(frozen-minus-adapted gap of roughly +10.1 to +10.4 return units).

**Practical implication:** this is a genuine, useful negative finding —
naive retraining on scenario-specific data is not guaranteed to improve
an offline-RL groundwater policy, and may substantially harm it,
plausibly through overfitting to a narrower data slice at the deep-
depletion end of the state space where the dataset's action support is
already thinnest (Section 17 above: 100% pumping is only 8.3% of
transitions, and deep-depletion states plausibly co-occur with heavier
extraction). The report is correct to scope this finding to the specific
adaptation procedure tested, not to domain adaptation, transfer
learning, or meta-RL methods in general.

## 55. Expanded Report: Behavioral Validation Against Real CGWB Observations

**Provenance (session integration, this revision):** this section is new
in this revision, added following a subsequent working session that
compared the Phase 4 simulator's rainfall-response dynamics against real
CGWB well observations — distinct from, and additional to, the purely
internal simulator self-consistency check already reported in Section
27 above (r = −0.13, simulated rainfall vs. simulated next-state change).

**Method:** for a sample of real CGWB wells, the empirical relationship
between observed rainfall (`chirps_roll3`, the same covariate used
throughout Phase 2) and the observed change in `currentlevel` between
consecutive quarterly readings was computed directly from the CGWB
dataset (Section 2), independent of the simulator entirely. This
observed relationship was then compared against the simulator's own
internal rainfall-to-next-state relationship (the same quantity
underlying Section 27's r = −0.13 figure, recomputed here specifically
for this comparison).

**Result:**

| Quantity | Value |
|---|---|
| Observed CGWB rainfall–response correlation (r_obs) | **−0.325** |
| Simulated rainfall–response correlation (r_sim) | **−0.117** |
| Sign match | **Yes** — both negative (more rain → shallower next reading) |
| Amplitude ratio (\|r_obs\| / \|r_sim\|) | **≈2.78** |

**Reading:** the simulator's rainfall-response direction is not
fabricated from nothing — it reproduces the correct, real-world sign of
the rainfall–groundwater relationship, and the two correlation
magnitudes are of the same sign and broadly the same order, with the
real observations showing a correlation roughly 2.8× as large in
absolute magnitude (|r_obs| / |r_sim| = 0.325 / 0.117 = 2.78). The
source document's earlier printed value of "≈1.23" was arithmetically
inconsistent with the two coefficients it also printed and has been
corrected here.

**Units and scope caveat (must accompany this comparison if cited):** the
observed and simulated quantities are constructed differently enough
that only the **sign** and **relative magnitude of the correlation
coefficient** are safely comparable — not the underlying regression
slopes or absolute effect sizes. The observed relationship is measured
in real physical units (mm rainfall vs. metres of `currentlevel` change,
at real well locations, over real elapsed time between CGWB campaigns,
which varies by well and season). The simulated relationship is
generated under A6's fixed-fraction recharge model (Section 24.1) inside
a discretized, uniform quarterly time step, with `recent_rainfall`
itself already a smoothed, seeded, and then randomly-drifting proxy
(Section 22), not a direct pass-through of real CHIRPS values after the
first step of any trajectory. Comparing raw slopes across these two
constructions would not be meaningful; comparing correlation sign and
rough magnitude, as done here, is the most that can be safely claimed.

**Practical implication:** this is genuine, useful evidence that A6
(Section 24.1) is not qualitatively wrong in direction, and provides a
weak, order-of-magnitude form of external validation beyond the purely
internal Section 27 check. It does **not** establish that A6's specific
functional form (a fixed fraction of `recent_rainfall`) or its numeric
recharge coefficient (0.15, Section 24.2) is calibrated to real
hydrology — a correct correlation sign and a roughly comparable
correlation magnitude are a much weaker claim than a validated
regression slope or a physically calibrated infiltration model. This
finding is cross-referenced from `limitations.md`, Section 11 (A6's
assumption entry) and Section 13.

**Resolved (end-of-session integration).** Source-level inspection confirms `cgwb_behavioral_validation.py` reads:

- `data/held_out_wells/held_out_ids.csv` (line 27) — for the observed-side CGWB relationship
- `data/processed/well_level_features_holdout.csv` (line 36) — for the CHIRPS covariate match
- `data/processed/offline_rl_dataset.h5` — for the simulator side

**The r_obs = −0.325 sample is held-out wells only**, not training wells and not a mix. This is a deliberate, methodologically consistent choice: the behavioral validation tests the simulator against the wells the project treats as unseen ground truth. Because the diagnostic is descriptive (simulator-vs-observation), not a model-training or model-selection step, it is consistent with the same "diagnostics do not consume the held-out-touch budget" discipline already documented for the ConvLSTM (§14.4) and the point_scale LSTM (§16.4).

## 56. A4/A5 Parameter Sensitivity of the 25 m Scenario Gap

**Provenance.** Closes §54.2's open item and `limitations.md` §29. Constructed after the earlier Phase-5 material to bound the single-number "+20.3 at 25 m" claim against the two assumption constants it depends on: A4 (`sustainability_threshold_m`, config-settable, canonical 15.0) and A5 (drawdown coefficient, hardcoded as `pumping_fraction * 2.0` in `synthetic_reward.step()` and `run_paper_experiments.scenario_step()`).

**Method.** A parameterized fork of `scenario_step` (`a4a5_sensitivity.py`) replaces A5 with a runtime argument; A4 is set via `reward_cfg["sustainability_threshold_m"]`. Grid: A4 ∈ {10, 15, 25} × A5 ∈ {1.0, 2.0, 3.0}. Each cell evaluated under all three scenarios (normal, drought, high) at gw_level = 25 m, using frozen BC/CQL checkpoints at `reports/paper_exp/frozen_models/`. Protocol: 200 episodes per seed, seeds 42/123/2024, paired bootstrap 5,000 replicates, seed 2026. Output: `reports/a4a5_sensitivity.json`.

**Results (CQL−BC return at gw=25, in 3×3 A4×A5 grid, canonical bold):**

| A4 ↓ \ A5 → | 1.0 | **2.0** | 3.0 |
|---|---|---|---|
| **10.0** | +24.2 | +54.9 | +79.3 |
| **15.0** | +7.6 | **+19.7** | +29.8 |
| **25.0** | +0.35 | +3.8 | +7.0 |

**Scenario invariance.** Within any (A4, A5) cell, `normal`/`drought`/`high` differ by less than 0.5 return units. Example, A4=15, A5=2: normal +19.72, drought +19.69, high +19.68. Scenario robustness holds at these depths.

**Parameter sensitivity.** The magnitude varies 226× across the grid (+0.35 to +79.3). The single number "+20.3" from §45 corresponds to the canonical (A4=15, A5=2) cell only. **Sign never flips:** all 27 cells have CQL−BC positive and all 27 bootstrap CIs exclude zero.

**Interpretation.** The CQL advantage at 25 m depth is **qualitatively robust** but **quantitatively parameter-dependent**. Any published magnitude from §45 must be reported as the value at canonical A4/A5 parameters, with the range stated. The 226× spread is itself a finding about how strongly these two uncalibrated assumption constants interact with the deep-depletion regime — consistent with `limitations.md` §29's caveat that A4/A5 are not hydrogeologically validated.

**Caveats.** 200 episodes per cell (vs. 500 in `compare_policies.py`) — adequate for a range check, less precise than the production protocol. 3 seeds only, consistent with every other Phase-5 result. Does not vary the reward *weights* (w1/w2/w3) — those are §47's separate ablation.
